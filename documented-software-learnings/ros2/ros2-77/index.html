Kalman Filter Node in Python: Angular Velocity from Odometry and IMU

Introduction

The robot now has two ways to know how fast it turns. The wheels give odometry, and chapter 69 made that odometry noisy on purpose, the way a real encoder is wrong: a small random Gaussian error on every wheel reading, published on bumperbot_controller/odom_noisy (What Gaussian noise means). Chapter 70 started that node next to the simple controller with slightly wrong wheel sizes as well (Launch Noisy Controller), and chapter 71 showed how much the noisy speeds shake (Put the two speeds in the graph). The IMU of chapter 75 measures the turning speed in a completely different way, with a gyroscope, and publishes it on imu/out (Terminal 3: read the IMU topic).

Chapter 76 explained how a Kalman filter combines two uncertain sources: a measurement update that makes the belief narrower (Bayes filters and the measurement update) and a state prediction that moves it and makes it wider, repeated in a loop (Motion update and the Kalman loop). This chapter turns that loop into a ROS 2 node, kalman_filter.py. It is a one-dimensional Kalman filter: it estimates one number only, the angular velocity of the robot around the z axis. The noisy wheel odometry gives the first guess and the motion of each step, and the IMU gives the measurement that reduces the error the encoders bring in. The result is published as a new Odometry message on bumperbot_controller/odom_kalman.

What must already work

The noisy controller of chapters 69 and 70 and the IMU of chapter 75 must already build and run in the simulation. This chapter creates a new package, bumperbot_localization, writes the node and builds it. Starting the filter and comparing its output comes next.

The idea in one picture

The filter keeps its knowledge about the turning speed as one Gaussian, called the belief: its mean is the best guess, its variance says how unsure that guess is. Three steps change it:

  1. Initialisation. A first guess, taken from the first wheel odometry message.
  2. Measurement update. A new IMU reading is combined with the belief. Two Gaussians are multiplied, and the result is narrower: the belief becomes surer.
  3. State prediction. The robot moves, so the belief moves with it. Two Gaussians are added, and the result is wider: moving adds uncertainty.

After the initialisation the measurement update and the state prediction repeat for ever: the curve gets narrower, then wider, then narrower again.

The widget below runs this loop with example readings. The first odometry message sets the start; each round then predicts with the change of the wheel speed and corrects with the IMU. The two sliders are the two variances the node uses: motion_variance_ (4.0) and measurement_variance_ (0.5). Every number is shown with its working.

Set up the package

Create the package

The filter gets its own package, bumperbot_localization. It uses the default build type, ament_cmake, which allows both Python and C++ nodes in the same package (the same setup as chapter 42). Go to the workspace, then to its src folder, where all the packages of the robot live:

cd bumperbot_ws
cd src
ros2 pkg create --build-type ament_cmake bumperbot_localization

Then back to the workspace, and build it once so that it also knows the new package:

cd ..
colcon build

The Python folder and files

An ament_cmake package does not create a folder for Python code by itself. In VS Code, inside the package bumperbot_localization, create a folder with the same name, bumperbot_localization:

Inside this folder create an empty file __init__.py. It marks the folder as a Python package; the ament_cmake build type does not create it automatically.

In the same folder create one more file, kalman_filter.py. The whole filter goes into this file.

Step 1: initialisation

The idea

At the very start the node knows nothing about the angular velocity. So it starts with a Gaussian that has mean 0 and a huge variance, 1000. A variance of 1000 is a standard deviation of √1000 = 31.6 rad/s: the curve is almost flat, it says that every speed is about equally likely. The first odometry message then gives a much better first guess for free: the angular velocity the wheel encoders measured. That value becomes the mean.

The node and its connections

The file starts like every Python node so far: the line that names the Python interpreter (needed because CMake installs the file and cannot detect the interpreter by itself), the rclpy library and its Node class, and the two message types: Odometry from nav_msgs (met in chapter 65) and Imu from sensor_msgs.

#!/usr/bin/env python3
import rclpy
from rclpy.node import Node
from nav_msgs.msg import Odometry
from sensor_msgs.msg import Imu

The class KalmanFilter inherits from Node, and its constructor names the node kalman_filter. Then come two subscribers and one publisher, each with a queue size of 10:

class KalmanFilter(Node):

    def __init__(self):
        super().__init__("kalman_filter")
        self.odom_sub_ = self.create_subscription(Odometry, "bumperbot_controller/odom_noisy", self.odomCallback, 10)
        self.imu_sub_ = self.create_subscription(Imu, "imu/out", self.imuCallback, 10)
        self.odom_pub_ = self.create_publisher(Odometry, "bumperbot_controller/odom_kalman", 10)
  • odom_sub_ reads the noisy odometry, the one to be filtered, on bumperbot_controller/odom_noisy. Each message runs odomCallback.
  • imu_sub_ reads the IMU messages on imu/out, from the IMU simulated in Gazebo or the one on the real robot. Each message runs imuCallback. A first version of this line used another topic name: the IMU publishes on imu/out, so that is the name to use. A wrong name gives no error; the IMU is simply never heard.
  • odom_pub_ publishes the result of the filter as Odometry messages on bumperbot_controller/odom_kalman, a different name from odom_noisy.

The starting belief and the other variables

Still in the constructor, the variables the filter works with:

# Initially the robot has no idea about how fast is going
self.mean_ = 0.0
self.variance_ = 1000.0

# Modeling the uncertainty of the sensor and the motion
self.motion_variance_ = 4.0
self.measurement_variance_ = 0.5

# Store the messages - only for the orientation
self.imu_angular_z_ = 0.0

self.is_first_odom_ = True
self.last_angular_z_ = 0.0
self.motion_ = 0.0

# Publish the filtered odometry message
self.kalman_odom_ = Odometry()

The two variances 4.0 and 0.5 are only estimates. Their job is to set up the filter so that the motion from the wheels counts as much more uncertain (much noisier) than the inertial measurement: 4.0 is 8 times 0.5.

The IMU callback

Every IMU message only stores its angular velocity around z. No maths happens here; the next odometry message uses the stored value.

def imuCallback(self, imu):
    # Store the measurement update
    self.imu_angular_z_ = imu.angular_velocity.z

The first odometry message

Each odometry message first copies the received message into kalman_odom_: the filtered message starts exactly equal to the noisy one, and later only its angular velocity is replaced. If this is the first odometry message, its angular velocity becomes both last_angular_z_ and the first guess mean_, is_first_odom_ turns False, and return ends this first run: nothing is predicted, updated or published yet.

def odomCallback(self, odom):
    self.kalman_odom_ = odom

    if self.is_first_odom_:
        self.last_angular_z_ = odom.twist.twist.angular.z
        self.is_first_odom_ = False
        self.mean_ = odom.twist.twist.angular.z
        return

Example: the first message says angular.z = 0.48 rad/s. After it, mean_ = 0.48 and last_angular_z_ = 0.48, while variance_ stays 1000.0. From the next message on, the two other steps run.

Step 2: measurement update

The idea

The measurement update says how to update the prior belief with new evidence, here a new reading from the IMU. Two Gaussians meet:

  • The prior belief: what the filter thinks before the reading. Its mean is called μ1 and its variance σ1². At first it comes from the wheel encoders; later it is the result of the prediction.
  • The measurement: the IMU reading as a Gaussian, with mean μ2 (the measured angular velocity) and variance σ2². It is assumed to be smaller than the uncertainty of the prior belief.

The measurement update multiplies the two Gaussians. The product is again a Gaussian, the posterior, with mean μ3 and variance σ3²: a better estimate of the angular velocity based on the new sensor information. The formulas for the product of two Gaussians were met in chapter 68:

μ3 = (σ2²·μ1 + σ1²·μ2) / (σ2² + σ1²)
σ3² = 1 / (1/σ2² + 1/σ1²)

Look at the top of the mean formula: each mean is multiplied by the other Gaussian's variance. The surer source (smaller variance) therefore gets the bigger weight, which is the idea of who to trust now in chapter 72.

One example with numbers

A prior belief with μ1 = 0.55 rad/s and σ1² = 4.5, and an IMU reading μ2 = 0.52 rad/s with σ2² = 0.5:

  • μ3 = (0.5 × 0.55 + 4.5 × 0.52) / (0.5 + 4.5) = (0.275 + 2.34) / 5 = 2.615 / 5 = 0.523 rad/s
  • σ3² = 1 / (1/0.5 + 1/4.5) = 1 / (2 + 0.2222) = 1 / 2.2222 = 0.45

The new mean 0.523 sits much closer to the IMU (0.52) than to the prior (0.55), because the IMU variance is smaller. The new variance 0.45 is smaller than both 4.5 and 0.5: the belief is surer than either source alone.

The code

In measurementUpdate the letters become the variables of the node: μ1 is mean_, σ1² is variance_, μ2 is imu_angular_z_ and σ2² is measurement_variance_.

def measurementUpdate(self):
    self.mean_ = (self.measurement_variance_ * self.mean_ + self.variance_ * self.imu_angular_z_) \
               / (self.variance_ + self.measurement_variance_)

    self.variance_ = (self.variance_ * self.measurement_variance_) \
                   / (self.variance_ + self.measurement_variance_)

The new mean is the measurement variance times the old mean, plus the variance times the IMU reading, all divided by the sum of the two variances: exactly μ3. The new variance is written as the product of the two variances divided by their sum, (σ1² × σ2²) / (σ1² + σ2²). It gives the same number as the formula above: with the example, (4.5 × 0.5) / (4.5 + 0.5) = 2.25 / 5 = 0.45. The backslash at the end of a line only continues the line on the next one. The mean must be computed first, because it still needs the old variance.

After this function mean_ holds the new estimate of the angular velocity and variance_ its new variance: together they are the new Gaussian, based on the evidence from the inertial sensor.

Step 3: state prediction

The idea

The measurement update gives an estimate of the current angular velocity. Its result is the starting point of the state prediction, the prior belief of this step, with mean μ1 and variance σ1². Starting from this estimate the robot moves, so its angular velocity changes by an amount the wheel encoders can estimate. That change, the motion, is a second Gaussian with mean μ2 and variance σ2².

The state prediction adds the two Gaussians. The sum is again a Gaussian, the posterior of this step, with the sum formulas of chapter 68:

μ3 = μ1 + μ2
σ3² = σ1² + σ2²

One example with numbers

Start from the result of the example in step 2: μ1 = 0.523 and σ1² = 0.45. The last odometry message said 0.48 rad/s and the new one says 0.55 rad/s, and the motion variance is 4.0:

  • motion μ2 = new odometry minus last odometry = 0.55 minus 0.48 = 0.07 rad/s
  • μ3 = 0.523 + 0.07 = 0.593 rad/s
  • σ3² = 0.45 + 4.0 = 4.45

The curve moves by the motion and gets about ten times wider: moving always adds uncertainty, and the next IMU reading will make it narrow again.

The code

First the motion, in odomCallback: the angular velocity of this odometry message minus the one stored at the previous message, last_angular_z_.

self.motion_ = odom.twist.twist.angular.z - self.last_angular_z_

Then statePrediction: the old mean plus the motion, and the old variance plus the motion variance.

def statePrediction(self):
    self.mean_ = self.mean_ + self.motion_
    self.variance_ = self.variance_ + self.motion_variance_

The loop inside odomCallback

Every odometry message after the first runs one round of the loop. The motion is known as soon as the message arrives, so the round starts with the prediction and ends with the correction by the newest IMU reading. Then this message's angular velocity is stored for the next motion, and the best estimate, the mean of the Gaussian, replaces the angular velocity in kalman_odom_, which is published on odom_kalman.

self.motion_ = odom.twist.twist.angular.z - self.last_angular_z_

self.statePrediction()
self.measurementUpdate()

# Update for the next iteration
self.last_angular_z_ = odom.twist.twist.angular.z

# Update and publish the filtered odom message
self.kalman_odom_.twist.twist.angular.z = self.mean_
self.odom_pub_.publish(self.kalman_odom_)

main

Last, the main function: initialise the ROS 2 interface, create the node, keep it running with rclpy.spin, and after Ctrl+C destroy the node and shut ROS 2 down.

def main():
    rclpy.init()

    kalman_filter = KalmanFilter()
    rclpy.spin(kalman_filter)

    kalman_filter.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()

The whole program

The code

The complete kalman_filter.py, 86 lines:

#!/usr/bin/env python3
import rclpy
from rclpy.node import Node
from nav_msgs.msg import Odometry
from sensor_msgs.msg import Imu


class KalmanFilter(Node):

    def __init__(self):
        super().__init__("kalman_filter")
        self.odom_sub_ = self.create_subscription(Odometry, "bumperbot_controller/odom_noisy", self.odomCallback, 10)
        self.imu_sub_ = self.create_subscription(Imu, "imu/out", self.imuCallback, 10)
        self.odom_pub_ = self.create_publisher(Odometry, "bumperbot_controller/odom_kalman", 10)
        
        # Initially the robot has no idea about how fast is going
        self.mean_ = 0.0
        self.variance_ = 1000.0

        # Modeling the uncertainty of the sensor and the motion
        self.motion_variance_ = 4.0
        self.measurement_variance_ = 0.5

        # Store the messages - only for the orientation
        self.imu_angular_z_ = 0.0

        self.is_first_odom_ = True
        self.last_angular_z_ = 0.0
        self.motion_ = 0.0

        # Publish the filtered odometry message
        self.kalman_odom_ = Odometry()


    def odomCallback(self, odom):
        self.kalman_odom_ = odom

        if self.is_first_odom_:
            self.last_angular_z_ = odom.twist.twist.angular.z
            self.is_first_odom_ = False
            self.mean_ = odom.twist.twist.angular.z
            return
        
        self.motion_ = odom.twist.twist.angular.z - self.last_angular_z_

        self.statePrediction()
        self.measurementUpdate()

        # Update for the next iteration
        self.last_angular_z_ = odom.twist.twist.angular.z

        # Update and publish the filtered odom message
        self.kalman_odom_.twist.twist.angular.z = self.mean_
        self.odom_pub_.publish(self.kalman_odom_)


    def imuCallback(self, imu):
        # Store the measurement update
        self.imu_angular_z_ = imu.angular_velocity.z


    def measurementUpdate(self):
        self.mean_ = (self.measurement_variance_ * self.mean_ + self.variance_ * self.imu_angular_z_) \
                   / (self.variance_ + self.measurement_variance_)
                     
        self.variance_ = (self.variance_ * self.measurement_variance_) \
                       / (self.variance_ + self.measurement_variance_)


    def statePrediction(self):
        self.mean_ = self.mean_ + self.motion_
        self.variance_ = self.variance_ + self.motion_variance_


def main():
    rclpy.init()

    kalman_filter = KalmanFilter()
    rclpy.spin(kalman_filter)
    
    kalman_filter.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()

Remember

  • A one-dimensional Kalman filter estimates one number, here the angular velocity of the robot around z, as a Gaussian: mean_ is the best guess, variance_ how unsure it is.
  • Inputs: the noisy wheel odometry on bumperbot_controller/odom_noisy and the IMU on imu/out. Output: an Odometry message with the filtered angular velocity on bumperbot_controller/odom_kalman.
  • Step 1, initialisation: start with mean 0 and variance 1000 (knowing nothing); the first odometry message sets the mean, then returns.
  • Step 2, measurement update: multiply the belief and the IMU Gaussian. μ3 = (σ2²·μ1 + σ1²·μ2) / (σ2² + σ1²), σ3² = 1 / (1/σ2² + 1/σ1²). The result is narrower than both.
  • Step 3, state prediction: add the motion Gaussian. motion = new odometry minus last odometry; μ3 = μ1 + μ2, σ3² = σ1² + σ2². The result moves and gets wider.
  • motion_variance_ = 4.0 and measurement_variance_ = 0.5 are estimates that make the IMU the trusted source.
  • In the code every odometry message after the first runs prediction, then update, then publishes mean_. The IMU callback only stores the newest reading.
  • A wrong IMU topic gives no error: the filter measures 0 for ever. The IMU publishes on imu/out.
  • The Python node lives in an ament_cmake package: a folder with the package name, an empty __init__.py, ament_python_install_package and install(PROGRAMS ...) in CMakeLists.txt, and the dependencies in package.xml.
